> 需求对应：[需求文档](需求文档.md) | 功能清单：[功能清单](功能清单.md)

## 1. 概述

本报告对比 NewLife.Office 与市面上主流 .NET 办公自动化库，覆盖 **Excel、Word、PPT、PDF、Markdown、RTF、ODS、Email、iCalendar、vCard、EPUB、XPS** 以及 OLE2/BIFF8 老式二进制格式，从功能覆盖、性能、依赖、许可等维度进行综合评估，为 NewLife.Office 的功能规划提供参考。

NewLife.Office 当前定位：**功能全面、零外部依赖、MIT 许可**的 .NET 办公自动化库，覆盖 12+ 文档格式及 Rendering 渲染扩展包，全部功能已开发完成（主库 761 项测试通过）。

## 5. NewLife.Office 差异化定位

### 5.1 核心竞争力

| 维度 | NewLife.Office 优势 |
|------|-------------------|
| **功能全面** | Excel + Word + PPT + PDF 四大办公格式统一在一个库中 |
| **零外部依赖** | 不依赖 Open XML SDK / PDFium 等第三方库，直接操作文件结构 |
| **全框架** | net45 ~ net10 全覆盖，竞品大多放弃 net45 |
| **免费** | MIT 许可，无商业风险（对比 EPPlus/iText/Aspose） |
| **统一 API** | 四大格式 API 风格一致，学习成本低 |
| **高性能** | 直接操作底层结构，避免中间层开销 |
| **智能类型** | 内置长数字保护、身份证保护、百分比识别（Excel） |
| **生态集成** | 与 NewLife.Core/XCode 等深度集成 |

### 5.2 目标赛道

NewLife.Office 定位为：

> **功能全面、高性能、零门槛的 .NET 办公自动化库**

- **Excel**：覆盖主流 Excel 操作功能，支持样式、图表、透视表、条件格式、模板填充、对象映射
- **Word**：覆盖主流文档创建与编辑功能，支持高保真往返、AES 加密、邮件合并、格式转换
- **PPT**：覆盖主流演示文稿操作功能，支持形状、图表、母版、动画、跨文件合并
- **PDF**：覆盖主流 PDF 操作功能，支持创建、读取、编辑、加密签名、Fluent API
- **Markdown**：全格式双向转换中枢（MD↔docx/PDF/HTML/Excel/PPT/Word）
- **Rendering**：文档页面 → 图片渲染扩展包（独立 NuGet，依赖 SkiaSharp）

让开发者以 MIT 许可、零外部依赖完成绝大多数办公自动化任务，不再为商业许可困扰。

### 5.3 竞品对标

- **vs EPPlus**：完全免费，无商业许可限制，框架兼容性更好

#### PPT

## 6. 结论

NewLife.Office 定位为 **功能全面、零依赖、MIT 许可的 .NET 办公自动化库**，已完整实现 Excel、Word、PPT、PDF、Markdown、RTF、ODS、Email、iCalendar、vCard、EPUB、XPS 及 OLE2/BIFF8 老式格式的操作能力，并配套 Rendering 渲染扩展包。

### Excel 领域

已实现样式、合并、冻结、筛选、对象映射、DataTable、模板填充、图片、页面设置、图表、透视表、条件格式、命名范围、结构化表格、富文本、企业特性等全部能力。免费方案（vs EPPlus v5+ 商业收费）。

### Word 领域

市面上缺少一个**功能全面且免费**的 Word 操作库：
- MiniWord 功能过于简单（仅模板填充）
- NPOI/Open XML SDK 太重或太底层
- Aspose.Words 价格高昂

NewLife.Office 以直接操作 ZIP + XML 的方式实现了全面的 docx 读写，并具备 L3 级保真（模型 + RawXml 透传）、AES 加密、邮件合并等差异化能力。

### PPT 领域

.NET 生态中 PPT 操作库选择极为有限：

- Open XML SDK 太底层，开发效率低
- ShapeCrawler 功能还在完善中
- NPOI 的 PPT 模块成熟度不足
- Aspose.Slides 价格高昂

NewLife.Office 填补了这一空白，提供易用且功能全面的 PPT 操作能力（形状/图表/母版/动画/批注/跨文件合并）。

### PDF 领域

PDF 库的许可证问题是行业痛点：

- iText 7 的 AGPL 限制了闭源项目使用
- QuestPDF 对大企业收费，且仅支持生成
- PdfSharp 功能有限，PdfPig 仅读取

NewLife.Office 以 MIT 许可提供全面的 PDF 操作能力（创建/读取/编辑/加密签名/表单/内容流重建），填补市场空白。

### OLE2/BIFF8 领域

实现老式二进制格式的 .NET 库较少且质量参差：

- **NPOI**（Apache 2.0）：最完整的 xls/doc/ppt 支持，但体积大（~10MB），API 底层（来自 Java 移植），内存高；
- **ExcelDataReader**（MIT）：专注 xls 只读，轻量（<1MB），不支持写入；
- **POIFS/POI 生态**：Java 系，.NET 中无原生对等实现。

NewLife.Office 已从零实现 OLE2/CFB 容器层作为共用基础，并在其上实现 BIFF8（.xls 读写）、MS-DOC（.doc 读取）、MS-PPT（.ppt 读写，文本级写入），与 NPOI 同等兼容，并保持零依赖和 MIT 许可优势。

### Markdown 领域

- **vs Markdig**：独有 MD→Word/PDF 多格式转换 + 各格式→MD 全格式中枢，统一办公文档生态，全框架覆盖 (net45~net10)
- **vs ReverseMarkdown**：正向 MD→HTML/Word/PDF + 反向 HTML/Word→MD 双向转换
- **vs anydoc**：统一 AST 转换层（`IMarkdownDocumentExtractable`）已对标实现；内容识别格式（magic bytes）为远期演进方向

### 扩展格式领域

传统办公自动化库聚焦于 Excel/Word/PPT/PDF，扩展格式（Markdown/RTF/ODS/Email/iCalendar/vCard/EPUB/XPS）的高质量免费实现在 .NET 生态中较为分散或缺失。NewLife.Office 通过统一的零依赖方式覆盖这些格式，在 B 端系统集成场景（邮件处理、日历互通、联系人导入导出、电子书生成）形成独特竞争优势。

### 渲染扩展（Rendering）

文档页面 → 图片渲染（PDF 直接渲染，Word/PPT/Markdown 经 PDF 中转），依赖 SkiaSharp 独立成包，与主库零依赖定位隔离，覆盖在线预览/缩略图场景。

| 维度 | NewLife.Office | NPOI | Aspose（全套） |

## 9. 功能遴选结论

竞品分析为功能规划提供遴选依据。以下将竞品洞察映射到功能清单，说明各能力的采纳/暂缓/否决结论。

| 竞品洞察 | 遴选结论 | 功能清单对应 |
|----------|---------|-------------|
| 声明式 Fluent PDF 生成成为主流方向 | 采纳：实现声明式布局 + 自动分页 | P07 Fluent PDF 生成 |
| 文档 → Markdown 统一 AST 是 AI 知识库入口 | 采纳：统一 AST 转换层 + 全格式转换中枢 | MD07 全格式转换中枢 |
| HTML → Markdown 反向转换需求明确 | 采纳：可配置的 HtmlToMarkdownConverter | MD04 反向格式转换 |
| 高级 Markdown 扩展（自动链接/脚注/公式/Emoji 等） | 采纳：管线 + 扩展注册机制 | MD05/MD06 |
| 文档页 → 图片渲染（预览/缩略图） | 采纳：独立 Rendering 扩展包隔离渲染依赖 | REN 渲染扩展包 |
| magic bytes 内容识别 | 采纳：已实现 `OfficeFactory.Detect()` 按文件头识别，不依赖扩展名 | GEN-1 内容识别 |
| 老式二进制格式迁移 | 采纳：OLE2/CFB 基础层 + BIFF8/MS-DOC/MS-PPT | OLE / M17 / W07 / S08 |
| 外部进程转换（如 LibreOffice） | 否决：与零依赖定位冲突 | 需求文档"不做什么" |

> 遴选原则：与"零外部依赖 + MIT 免费"定位冲突的能力优先否决或拆分为独立扩展包；需求明确且成本可控的能力优先采纳。
